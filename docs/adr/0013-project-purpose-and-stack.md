# 0013. Назначение проекта и стек: патченный форк RacingDSX 0.6.7

- Status: Accepted
- Date: 2026-10-19

## Relations

- Depends-on: none
- Supersedes: none
- Constrains: none
- Related: 0003

## Context

Решение фактически принято в начале работы (ADR-0001…0007 от 2026-09-09 уже его
предполагают), но записано только сейчас, вместе с переходом на шаблон ADR-0011.

У пользователя уже стоял RacingDSX из апстрим-релиза
[cosmii02/RacingDSX](https://github.com/cosmii02/RacingDSX) версии 0.6.7: `RacingDSX.exe`,
`RacingDSX.dll.config` и настроенный под себя `RacingDSX.json`. С FH4/FH5 он работал. С
Forza Horizon 6 появилось залипание руления (ADR-0001) и тугие триггеры в меню (ADR-0002).
Задача — чтобы та же программа работала с FH6, а не новая функциональность.

Что из себя представляет апстрим (проверено по первому коммиту `4dec5eb`, тег `upstream-0.6.7`):

- C#, `net8.0-windows`, WinForms (`UseWindowsForms`), `OutputType = WinExe`, `win-x64`;
  лицензия GPLv3 (`RacingDSX_source/LICENSE`);
- парсеры Forza (FM7, FM8, FH4/FH5) и Dirt Rally, профили игр, AppCheck по именам процессов,
  вкладки настроек тормозного и газового триггеров, конфиг `RacingDSX.json`.

Границы интеграции, которые задаёт апстрим и которые мы не меняем:

```
Forza --UDP 5300 (Data Out)--> RacingDSX --UDP 6969 (JSON)--> DSX --HID--> DualSense
                                                               └--> виртуальный X360-пад (ViGEm) --> Forza читает стики
```

- **Вход:** Forza Data Out, UDP на `gameUDPPort` профиля (по умолчанию 5300). Формат
  определяется длиной датаграммы (ADR-0003).
- **Выход:** UDP API программы DSX на `127.0.0.1:DSXPort` (по умолчанию 6969):
  `{"instructions":[{"type":…,"parameters":[…]}]}`, параметры позиционные.
- **DSX** владеет HID-устройством DualSense и виртуальным падом ViGEm. RacingDSX не читает и
  не пишет стики и кнопки, он только задаёт режимы триггеров и цвет лайтбара. Поэтому сломать
  руление он может только перегрузкой DSX (ADR-0001).

Вся цепочка работает только на Windows: игра на ПК, DSX, драйвер ViGEm, WinForms и
`net8.0-windows`.

Разница с апстримом после всех правок до 2026-10-11 — 11 файлов, +542/−240 строк
(`git diff upstream-0.6.7 --stat -- RacingDSX_source`): путь отправки в `RacingDSXWorker`,
логика тормоза в `Parser`, тема и обработчики в UI.

## Considered options

1. **Патченный форк апстрима 0.6.7 на его же стеке.** Ошибка была в пути отправки, а не в
   архитектуре: формат пакета FH6 совпадает с FH5 (ADR-0003). Исправление укладывается в
   несколько сотен строк. Пользователь сохраняет свой конфиг, раскладку файлов и привычный
   интерфейс. Минус — наследуем долги апстрима: статические сокеты (ADR-0004), глобальный
   `FMData.BufferOffset`, дизайнерский WinForms, который здесь нельзя открыть без Visual Studio
   (ADR-0005), отсутствие тестов (ADR-0007).
2. **Написать свою программу с нуля** (на любом стеке). Пришлось бы заново сделать парсеры
   Forza и Dirt, профили, AppCheck, интерфейс настроек и перенести конфиг пользователя. Объём
   на порядок больше исправления, а новые ошибки в уже работавших местах вероятнее, чем выигрыш.
3. **Ждать исправления в апстриме.** Неизвестно, будет ли оно и когда. Пользователь играет
   в FH6 сейчас.
4. **Сменить стек апстрима** (.NET 9 ради системной тёмной темы, WPF, кроссплатформенный UI).
   Ни одна из проблем FH6 со стеком не связана. Переход дал бы расхождение с апстримом и
   переустановку рантайма у пользователя без пользы. Кроссплатформенность бессмысленна: DSX и
   ViGEm есть только под Windows.
5. **Управлять DualSense напрямую по HID, без DSX.** Тогда пришлось бы самим делать и
   HID-вывод, и виртуальный пад для игры, то есть повторить DSX. Пользователь уже работает
   через DSX, и именно его пад читает игра.

Для хранения:

6. **Весь каталог проекта в git, включая собранный exe и `RacingDSX.json`.** Любой
   `checkout` или `reset` мог бы перезаписать живой настроенный конфиг пользователя.
7. **Без системы контроля версий**, откат через `backup_original/` и `*.bak` (так было до
   2026-10-11, см. обновление ADR-0006). Не видно, что именно форк поменял в апстриме.

## Decision

Вариант 1 и раздельное хранение исходников и развёрнутой сборки:

- Проект — патченный форк RacingDSX 0.6.7. Язык, фреймворк и UI остаются апстримными:
  C#, .NET 8 (`net8.0-windows`), WinForms. Платформа — только Windows.
- Границы интеграции остаются апстримными: вход — Forza Data Out по UDP, выход — UDP JSON API
  DSX. RacingDSX не трогает стики и кнопки, HID и виртуальный пад — зона DSX.
- Правки делаются минимальными и в стиле окружающего кода. Апстрим-код не переформатируется
  и не «чистится» попутно, чтобы `git diff upstream-0.6.7 -- RacingDSX_source` показывал только
  смысловые изменения.
- Git: первый коммит (`4dec5eb`, тег `upstream-0.6.7`) — неизменённый исходник апстрима из
  архива ветки main, без артефактов сборки и состояния IDE. Все изменения форка — следующими
  коммитами.
- `RacingDSX_exe/` (собранный exe, живой `RacingDSX.json`, `backup_original/`,
  `backup_prev/`) намеренно вне git (`.gitignore`). Ни одна git-операция не должна его касаться.
  Способ сборки и развёртывания — ADR-0006.

## Consequences

- Пользователь меняет exe один к одному и ничего не переустанавливает (ADR-0006).
- Долги апстрима остаются, и их нужно учитывать при каждом изменении: статические сокеты и
  один воркер (ADR-0004), глобальный `BufferOffset` (ADR-0003), правка UI только текстом
  (ADR-0005), тесты только чёрным ящиком (ADR-0007).
- Новые возможности упираются в DSX UDP API: всё, чего нет в его инструкциях, RacingDSX
  сделать не может.
- Любое увеличение исходящего трафика в DSX — риск вернуть залипание руления (ADR-0001).
- Отказ от .NET 9 закрывает путь к системной тёмной теме WinForms (ADR-0005).
- Откат исходников — через git, откат развёрнутой сборки — только через резервные копии в
  `RacingDSX_exe/`. Перед заменой файла там нужна копия.
- Изменения апстрима после 0.6.7 сами не приходят: remote нет, слияние — ручная работа поверх
  тега `upstream-0.6.7`.
- Затронуто: весь `RacingDSX_source/`, `.gitignore`, `RacingDSX_exe/` (вне git).
